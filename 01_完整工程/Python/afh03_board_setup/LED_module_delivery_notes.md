# ⚠️ 给用户的第一承诺：**我们宁可不判，也绝不误报**

> 这条比"覆盖率/识别率"更重要 —— **用户最怕的是"错报正常"，而不是"某种条件下不判"**。

**实测依据（G5 汉字状态屏，15 档退化矩阵）**：缩放 0.6/0.8/1.2、旋转 ±2°/±5°、模糊 r=1/2、
亮度 0.7/1.3、对比 0.7/1.3、加 2 个反光斑 ——
**没有任何一次错报 `✅正常`**；凡超出当前能力的条件，输出一律是 **`⚠ 未判定` + 具体原因**（低置信/读数不符）。

**已知退化边界（会在页面上以"未判定"呈现，不会给出错误结论）**：
* 残余滚转 **> ±2°**（手持/非水平时要注意；滚转补偿正在重做）
* 亮度或对比 **+30%** 以上
* 标记：总边长须落在 **`[max(24, 1.5%×短边), 25%×短边]` px** 区间内（太大的标记会被拒并提示"拉远或换 15mm 版"）

**当前可给结论的部分（已板端验证）**：
* **G5 汉字状态屏**：`天线方向=正常`、`自检状态=正常` ⇒ **`✅ 正常（自动判定·未标定）`**
* **G1~G4**（电源指示/工频电源/换向与发射机控制/发射机状态）：标记识别 → 规则判定，8 条真值 **亮灯数 8/8、漏检 0、误检 0**
* 标记识别正/负样本回归 **9/9 = 100%**（负样本 0 假阳性）

（详细证据与六条跨组/算法/评测纪律见 **附录 B**；现场操作铁律见 **附录 A**。）


> 本文档是 LED 这一块的使用与验收说明。配套：`config/led_rules.json`（规则表）、`tools/led_photo_verdict.py`（照片跑批）、

# 📋 现场装配与验收清单（照着做，目标 **30 分钟装完并验收**）

> **两种用法都支持**：① **标记贴在部件旁**（主用法：判定时标记与部件同框）
> ② **手持标记**对镜头（兜底：靠"身份锁定" —— 识别后 5s 内转向部件即可判定）
> **第一天无需标定**：标记定身份 + 自动判定档即可出结论；**标定是可选增强**（可精确到"哪颗灯不正常"）。

## 1. 结论怎么给（用户口径，已收敛）

**拍一张照片 → 只输出两样**：

```
✅ 正常            或            ❌ 故障
依据：3 颗灯全亮 → 供电正常         依据：控制灯不亮 → 供电差错
```

三态：`✅ 正常` / `❌ 故障` / `⚠ 未判定`。
**未标定、证据不足、部件认不出 → 一律"未判定"**，绝不把"不知道"说成"正常"或"故障"。

★ **不能用全局假设**：同为红灯，`天线启动` 亮=**正常**，而 `发射机状态·故障` 灯亮=**故障** → 必须按部件套规则 ✔

## 3. 判据怎么做的（含一条"实测推翻假设"的教训）

| 环节 | 做法 | 实测依据 |
|---|---|---|
| **ON/OFF 主判据** | **亮点掩膜命中（自发光）**：红/绿高饱和 **或** 过曝白芯 `V>240 & S<90`；**再用 `delta = 中心盘 − 外围暗环(2.2~3.2×灯径, P25)` 交叉校验** | 真灯 delta **45.2~193**；**但暗灯罩反光也会 delta≥25** → 单用 delta 曾出现 **3 处误检**（判定从 8/8 掉到 5/8） |
| **颜色** | 只做**分类**（红/绿），**不作亮灭门槛**；过曝时用"各通道相对暗环的增量"判色 | 过曝白芯 `R≈G≈B`，按饱和度判会把亮的灯判成灭 |
| **按钮≠灯** | `通`/`断` 方按钮、拨杆：自发光弱（delta≈0）+ 形状非圆（fill/长宽比不符）→ 排除 | 现场 0 误检 ✔ |
| **眩光/丝印白点** | 半径过滤（真灯 r≈19~31 px @长边1536；白点 r≤8）+ 尺寸一致性 | ③全灭照片里只有 2 个 r=4 白点，已排除 |
| **朝向归一** | 横拍（宽>高）→ 顺时针 90°；**8 张真值全无 EXIF 朝向**，只能按几何判 | `151324/151341/151359/151448` 需要转 |
| **迟滞+去抖** | `delta≥25` 亮 / `≤15` 灭，中间保持；连续 3 帧一致才改状态 | — |
| **FPGA 优先** | 有状态字时以 FPGA 的 LIT 位为准，软件值并列保留（`source=fpga`） | — |
| **防误检门** | ①ROI 未标定/越界/半径超界/灯数与规则不符 → 未判定 ②**几何门**：亮点数>部件灯数、灯径差>2.2×、≥3 灯不共线 → 未判定 | `151104`→未判定 ✔；`151631`（67 个亮点）→未判定 ✔ |

> ⚠️ **教训（写进交付）**：起初按"ON = 中心盘 − 暗环 delta"实现，**实测出 3 处误检**后才改成
> "自发光掩膜 + delta 交叉校验"。**结论：不可用未经实测的单判据；暗灯罩反光必须靠"是否自发光"区分。**

# 附录 A（2026-10-05 补）：现场三条铁律 + 标定/标记流程 + 回滚

> 本附录是**踩坑后固化下来的操作纪律**，请现场务必遵守；每条都附实测数字。

## A.1 🚫 绝对不要在板子控制台上起第二个 X（会把可见屏抢走）
**现场事故**：屏上突然出现 **lightdm 登录界面**（`linaro` 账号），看不到我们的 UI。
**实测根因**：`cat /sys/class/tty/tty0/active` → **`tty8`**；`ps` 里出现**两个 X**：`Xorg :0 (tty7, 19:49 起)` + `Xorg :1 (tty8, 20:29 起)`；kiosk 跑在 `:0` 上 → **`:1` 把可见 VT 抢走**。
**我方引入的原因**：`systemd/afh03-ui.service` 里写了 `Wants=graphical.target`
→ systemd 会去拉 `graphical.target` → **lightdm 在 tty8 再开一个 X**。**已删除该行**（只保留 `After=`），并补 `Environment=XAUTHORITY=/home/linaro/.Xauthority`。

**纪律**：
* 离屏渲染界面图**只允许**用 `DISPLAY=:0`（配 `XAUTHORITY`）或纯离屏 `--render`（不需要 X）；**禁止** `startx`/`Xorg :1`；确需虚拟屏请用 **`Xvfb :99`**（不占 VT）。
* **恢复动作**（若又出现登录界面）：
  ```bash
  pkill -f 'Xorg :1'        # 结束误起的第二个 X
  chvt 7                    # 把可见屏切回 tty7（kiosk 所在）
  systemctl restart afh03-ui
  cat /sys/class/tty/tty0/active   # 应为 tty7
  ps -ef | grep '[X]org'           # 应只有 1 个 :0 / tty7
  ```

## A.4 🖐 触摸输入：本板是 **MT 协议 B**（不要读 ABS_X/ABS_Y）
**现场事故**：用户点【拍照】没反应。
**实测根因**：触摸 = `/dev/input/event3` = **`goodix-ts`**，其

**改法**：`soc_vision/touch_input.py` 按 MT-B 解析（`ABS_MT_SLOT/TRACKING_ID/POSITION_X|Y`，兼容 `ABS_X/Y` 与压力），按下/抬起都判并去抖成一次 tap；坐标按设备实际范围缩放。

## B.1 ★★ 「故障报不出来」的根因：几何门要求"亮点共线"是错的
**现场现象**：G1（电源指示，3 灯）在现场读到了标记、模块身份已确定，**结论却永远是"未判定"**：
```
verdict=未判定  reason=3 颗亮点不共线（垂轴偏差 314 px > 230）→ 不是同一排灯 → 未判定
```
**根因（关键）**：几何门当年是"**要求检测到的亮点成排/共线**"，但——
**没亮的灯根本检测不到！** 而"3 盏里只亮 1~2 盏"**正是"故障"要表达的状态** ⇒
只剩 1~2 个亮点 ⇒ 必然判"不共线" ⇒ **最该报出来的"故障"反而永远报不出来**。

**修法（已在 `soc_vision/led_panel.py: geometry_gate` 落地）**：
| 旧判据 | 新判据 |
|---|---|
| 亮点必须共线（≥3 点时校验垂轴偏差） | **取消共线要求**（没有预测排布时不阻断） |
| 亮点数必须 ≥ 期望 | **允许"检出 ≤ 期望"**（不亮的检不到是正常现象） |
| — | **只拒绝"多余亮点"**：`n_lit > expected_count` → 未判定（疑似混入别的发光体/反光） |
| 灯径一致性 | **保留**：`max_r ≤ 2.2 × min_r`，否则未判定 |

**修后实测（合成：G1 标记 + 3 灯里涂掉 2 颗，且**不给 `--auto`**）**：
```
[marker] 离屏识别到 G1（电源指示）→ 模块=PS_KONG
[marker] 判灯前已涂黑标记区
[capture] verdict=故障  reason=该部件应有 3 颗全亮，实测只亮 2 颗 → 供电差错（自动判定·未标定）
```
⇒ 从"永远未判定"变成 **`❌ 故障` + 一行依据 + 安全标注** ✔（安全边界仍在：多余亮点/灯径离谱/低置信 → 未判定）

## B.2 ★ 判灯前必须**涂黑标记占用的区域**
**现象**：贴上标记后，"3 灯全亮"那例变成 **4 个亮点** → 被"多余亮点"判据拒绝 → 未判定。
**原因**：4×4 标记的**白色模块**自身是亮块，会被亮度检测当成一颗"灯"。
**修法**：判灯前把标记所在区域涂黑（`ui_kiosk` 在 `run_capture` 前处理）。
⚠️ **已知残留**：`detect_markers()` 返回的 `side_px` 与"黑框外沿边长"语义不一致（实测贴 103px 的标记，`side_px` 报 **13px**）→ 当前涂黑半径偏小（r≈7px），**真标记没被完全涂掉**。
**待办修法**：`side_px` 改读 `Marker.s × 模块数`（4×4 标记 = 6 个模块含静区），并用 `px_per_mm` 自检（25.0mm ↔ 103px ⇒ `px_per_mm ≈ 4.1`）；涂黑改为**按标记实际 bbox 反算四角**，或半径 `max(side_px×3, 6%×短边)`。

## B.3 标记边长口径（**自适应，不要写死**）
* 实现：`min_side_px = max(16, 1.5% × 短边)`、`max_side_px = 0.98 × 短边`
* **实测**：用户现场那块 **G1 真实边长只有 41~46 px**，**自适应门成功接受并定出身份** ⇒ 我早先给的 **"≥60px"口径偏保守**，正式口径应为：
  **"自适应，≥1.5% 短边即可（实拍 41px 已验证可用）；A4 数字版面 49px 亦通过"**
* journal 会打**候选边长**：`[marker] 候选 1 个：G1(0.80,46px)（min_side=16 max_side=1056）` → 可据此指导用户"再靠近一点"

## B.4 预览卡顿的治本：**底板缓存**（不要用降 fps 换 CPU）
**实测成本与 fps 近似线性（≈9%/fps）**，且**标记检测线程不是瓶颈**：
| 配置 | python CPU | 预览 fps |
|---|---|---|
| 5 fps @1920×1080（旧） | 37.0% | 4.0 |
| 8 fps @1920×1080 | 89.0% | — |
| 12 fps @1920×1080 | 106% | 6.5 |
| 8 fps @1280×720 | 73.2% | 5.4 |
| **8 fps @1280×720 + 底板缓存（本版）** | 见板端实测（脚本 `measure_cache.sh`） | 见 journal `[ui] preview fps=` |

**做法**：静态部分（标题/按钮/提示/dbg/错误横幅/结论与依据）**只在"键"变化时渲染一次**成底板；

## B.6 ★ 「假设必须用数字检验」——一次被实测推翻的优化
**我的假设**："预览卡顿的 CPU 大头是**每帧重复渲染中文**（Pango）" → 于是做了**底板缓存**（静态字只画一次）。

## B.8 六条纪律（跨组/算法/评测通用，全部有实测支撑）

> 这一节是 2026-10-05 与 `fpga-roi-accel` 联合排查 G5 汉字状态屏时逐条踩出来的，
> 每条都附**当时的错误现象**与**正确的自证方式**，后人直接照做即可少走这些弯路。

### ① 参考侧 / 运行侧必须**共用同一个预处理函数**，并用"参考自匹配"自证
* **现象**：运行侧用 `to_bitmap`（灰度→缩放→二值化），参考侧用 `to_template_bitmap`（二值化→**裁到笔画外接框**→缩放→二值化）。
  差一个"裁框" ⇒ **逐格 NCC 与参考位图 mean = -0.063（几乎反相关）**，全表命中率只有 **36.4%**。
* **修法**：两侧共用 `to_template_bitmap` ⇒ 全表立刻 **36.4% → 78.8%**（+42pp）。
* **自证方式（关键）**：把**参考自己的位图**喂进运行管线，应 **top1 = 自身、66/66 = 100%**。
  本次正是靠它一眼区分"**预处理问题**"还是"**匹配问题**"（自证 100% ⇒ 匹配没问题 ⇒ 故障在预处理）。

### ② 跨组交接数据**先冻结 schema**，消费方做**键名兼容 + 双通道自证**
* **现象**：`cn_grid_v2.json` 的键名被改过：`roi_crop_box_orig` → `roi_crop_xywh_orig`/`roi_crop_xyxy_orig`、
  `roi_size` → `roi_size_wh`、`box_roi` → `box_roi_xywh` ⇒ 我按旧键读 **KeyError**。
* **修法**：四通道兼容（`roi_crop_xywh_orig` / `roi_crop_box_orig` / `mapping` 公式 / `roi_quad_orig` 包围盒），
  **两条通道解出同一结果才算过**：本次 `mapping` 公式与 `roi_quad_orig` 均得 **768,122,1320×2827（长宽比 0.467 = 653/1400）** ✔
* **纪律**：交付方**先冻结 schema**；消费方**绝不假设键名**。

### ③ 词表 DP **只能修 "top-3 之内" 的错**
* **现象**：行12 值列真值 `正常`，第二格 top-1 读成 `台`，而 `常` **不在该格 top-3** ⇒ 无论怎么加词表约束都拼不出 `正常`
  （硬约束 DP 实测 **19/56 → 19/56，零改善**）。
* **结论**：串约束**救不回"候选里没有的字"**；瓶颈在**单格精度**，不在串约束。

### ④ **不要以单字为目标调全局参数**（会过拟合）→ 用**多变体候选并集 + 硬约束**
* **现象**：以"参考库里 `常` 那格"为目标扫运行侧参数（阈值/padding/缩放核/极性），
  找到 `t=0.35/pad=8/bilinear` 让 `常` 的 NCC 从 0.455 → **0.625（该字修好了）**，
  但**全表从 78.8% 崩到 28.8%**、逐格 NCC 均值变负 ⇒ **典型过拟合**。
* **修法**：**保留全局默认不动**，把该组合作为**第二个生成器 B**，与生成器 A 做 **top-5 候选并集**
  ⇒ 全表 **78.8% → 80.3%**，且 `正`（来自 A）与 `常`（来自 B）**各取所长**，两行值列达成 **2/2 = 正常** ✔

### ⑤ 评测 harness **必须与判据同等自检**
* **现象（本组连续两次自伤）**：
  1. `final` 只覆盖 `value/label`（56 格），**10 格 `fkey` 从未初始化** ⇒ `None` 被计成"错"，

* **纪律（可执行形式）**：① **全类别覆盖自检**（`value/label/fkey/…` 一次建齐）
  ② "**未初始化绝不等于错**" ③ **报告命中率之前断言覆盖 == 总格数，不通过就中止输出**（宁可不报，也不报错数字）
  ④ **关键统计只允许一个初始化点**（禁止下游重置）。

### ⑥ 几何补偿类改动 **必须先证明"零改动时估计量恒为 0"**

## B.11 踩坑表 #27：**负向测试必须真正走到被保护的分支**
* **现象**：我为"检测帧必须全分辨率"加了启动断言，写负向用例时用了 `--no-camera`，
  而断言当时写在 `if not a.no_camera:` **分支内部** ⇒ **那次运行根本没走到断言**，输出为空，
  **"故意降检测帧会被拒"这件事其实并未被证明**（差点把它当成"已验证"写进结论）。
* **修法**：把断言**移出该分支**，让它对"**配置的采集尺寸**"独立生效 ⇒ 负向用例必定触发保护。
* **方法论（mutation 思路）**：写负向用例时先自问 ——
  **"如果我把这段保护去掉，这个用例会失败吗？"** 若答案是否，则该用例**证明不了任何东西**。
  "绕过了代码路径的测试"不是测试。


## B.12 踩坑表 #28：**CLI 参数必须证明"确实传到了生效点"**
* **现象**：我加了 `--max-side-frac` 参数，但**构造器调用那一处没接线**（补丁锚点没匹配到，
  我误以为已改）⇒ **静默 no-op**：行为"看起来正确"**只因为默认值恰好就是 0.50**。
  如果当时把默认值定成别的（或用户传了非默认值），就会**以为改好了其实没生效**。
* **修法**：① **启动时打印生效参数**（`[marker] 生效参数: max_side_frac=0.50 min_side=24 confirm_n=3 min_score=0.80`）
  ② 加**负向自测**：用 `--max-side-frac 0.10` 启动 → **断言日志里的生效值确实是 0.10**（未接线则必失败）。
* **方法论**：**改一个能触发行为差异的值，断言行为随之改变**；只验证"默认路径能跑"不能证明参数已接线。
